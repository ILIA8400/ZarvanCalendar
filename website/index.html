Zarvan Calendar

A Jalali calendar UI that survives your app.

Month, week, day, year and list views. Recurring events, filtering, highlighting and Excel export. Persian and right-to-left by design — no framework, no build step, no runtime dependencies, and nothing fetched at runtime.

Vanilla JavaScript Zero dependencies Script tag, no build step MIT TypeScript definitions
Live Real library, real events — open the menu, switch views, click anything.

What it is

Zarvan is a calendar interface for the web, written for the Jalali (Persian) calendar from the ground up. It is not a Gregorian calendar with a locale bolted on: the date arithmetic, the week that starts on Saturday, the right-to-left layout and the Persian numerals are the default path, not a branch you can get wrong.

You load it with a <script> tag and it lives on window.Zarvan. There is no bundler step, no module graph, and no package to resolve at runtime.

Why you might pick it

It survives your app's CSS

Every class is zc--prefixed and scoped, with a reset that neutralises the host's global rules. For hosts that fight dirty, shadow: true closes the last gap.

Themed by tokens

85 CSS custom properties cover colour, spacing, radius, typography, elevation and structure. You retheme by setting variables, not by winning specificity fights.

Light and dark

colorScheme: "auto" follows the system and keeps following it. Dark is the same tokens re-valued, so whatever you themed goes with it.

Operable from the keyboard

Roving tab stops in the day grids, a modal that traps focus, and a collapsed sidebar that is inert rather than an invisible detour through the tab order.

Loads what it shows

Pass a function instead of an array and the calendar asks for one visible range at a time, with ordering, de-duplication and caching handled for you.

Extensible without forking

Views and plugins are registered, not hardcoded. Highlighting, the now indicator and Excel export are themselves plugins.

Installation

Everything a consumer needs is in dist/. Copy the folder into wherever you serve static assets from and you are done — there is nothing to build, resolve or bundle.

Pinning it as a dependency

Zarvan is a <script>-tag library that lives on window. It is deliberately not an ES module or a CommonJS module, and its package.json declares no main or exports rather than claim otherwise. Pin a tag or a commit SHA and copy the folder across in a build step:

package.jsonjson
"dependencies": {
  "zarvan-calendar": "git+ssh://git@github.com/your-org/ZarvanCalendar.git#v3.0.3"
}
scripts/copy-zarvan.mjsjs
import { cpSync } from "node:fs";
cpSync("node_modules/zarvan-calendar/dist", "public/vendor/zarvan", { recursive: true });

Vendoring the folder straight into your own tree works just as well, and for a private fork it is usually simpler: no git-dependency auth in CI, and your SBOM tooling sees real files.

Do not import it

import Zarvan from "zarvan-calendar" will fail. There is no module entry point on purpose — declaring one would produce a confusing runtime failure instead of an honest one. Load the script tag and read window.Zarvan.

TypeScript

dist/zarvan.d.ts declares the Zarvan and jalaali globals. It contains no import or export on purpose: either would turn it into a module and the globals would stop being visible.

tsconfig.jsonjsonc
{ "include": ["src/**/*", "vendor/zarvan/zarvan.d.ts"] }
const cal = Zarvan.create({ selector: "#calendar", events: [] });
cal.setView("week");                    // ViewName is checked
cal.on("onEventClick", (ev, meta) => console.log(ev.title, meta.jdate?.jy));

The one optional dependency

The Excel export needs SheetJS, and it is neither bundled nor vendored. It is resolved when the export button is pressed — from options.deps.xlsx or window.XLSX. Without it the button reports through onWarn and nothing else changes. See Excel export.

Getting started

Basic usage

One call, two things that matter: where to render, and what to render. Everything else has a default that works.

Live Exactly the code below, running. 
const cal = Zarvan.create({
  selector: "#calendar",
  view: "month",
  events: [
    { id: 1, title: "جلسه طراحی", start: "1405-06-02T09:00", end: "1405-06-02T10:30", type: "meeting" },
    { id: 2, title: "اسپرینت",    start: "1405-06-03", end: "1405-06-05", allDay: true, type: "sprint" },
  ],
});

selector

A CSS selector string or an element. The element you pass is the one the calendar renders into — it gets the zc-calendar class, a dir="rtl" attribute and a data-zc-id stamp. If it cannot be found, create() throws rather than failing quietly. 

Zarvan.create({ selector: "#calendar" });                         // a selector
Zarvan.create({ selector: document.getElementById("calendar") }); // an element

When it renders

create() renders synchronously — the calendar is in the DOM by the time it returns. Every change after that is batched into one animation frame, so you can set several things in a row and pay for a single render. 

cal.setView("week");
cal.gotoDate({ jy: 1405, jm: 6, jd: 2 });
cal.setTypeStyles({ meeting: { bg: "#2563eb" } });
// …still one render, on the next frame.

cal.refresh();   // or: render whatever is pending, right now

If you would rather every change render immediately — in a test, say, where waiting for a frame is awkward — pass renderMode: "sync".

Tearing it down

destroy() releases every listener, interval, node and injected style tag, and hands the element back as it was found: the zc-calendar class, data-zc-id, dir/lang and every inline --zc-* property the instance wrote are all removed. Custom properties the host set on that element are left alone. 

const cal = Zarvan.create({ selector: "#calendar", events });

// …later, when the view unmounts
cal.destroy();
In a framework

Create in the mount hook, destroy in the unmount hook, and keep the instance in a ref rather than in reactive state — it is a long-lived object, not a value to diff. The repository's examples/ folder has working React and Vue wrappers that do exactly this.

Which options are hot

setOption(key, value) is deliberately narrow. Feature flags are hot, and so are view, locale, colorScheme, typeLabels, typeStyles, highlights and events. Anything structural was consumed while the instance was being built, so it warns with warn.optionNotHot rather than pretending to have worked. 

cal.setOption("features.nowLine", false);          // dotted paths work
cal.setOption("features.views.year", false);      // …to any depth
cal.setOption("features", { sidebar: false });    // or a patch object

cal.setOption("shadow", true);                    // warns: not hot, returns null
Merged, not replaced

A feature patch is merged into the existing object rather than swapping it out. Plugins and view contexts hold a reference to that object from construction, and replacing it would leave every one of them reading a stale copy.

Validation

Events are validated as they arrive. A malformed one is reported through onWarn with a stable code, and either dropped or kept and flagged. 

validation: {
  enabled: true,             // false skips the whole pass
  requireNumericId: false,   // reject events whose id is not a number
  onInvalid: "drop",         // "drop" (default) | "keep" — kept events get _invalid
  autoFix: true,             // repair an end that falls strictly before start
}

Views

The five views

Month, week, day, year and list. Each one knows the date range it covers, which date anchors it, how to step forward and back, and how to draw itself — which is exactly the contract a view you write yourself has to meet.

Live
The buttons call cal.setView(name). The calendar's own switcher in its header does the same thing — either way onViewChange fires, which is what you see logged.

What each one is for

ViewCoversSteps byGood for
monthOne Jalali monthOne month The default. A seven-column grid; each cell holds as many events as fit and collapses the rest into “+N more”.
weekSaturday → FridayOne week A 24-hour time grid across seven columns, with an all-day row above it and the now indicator on today's column.
dayOne dayOne day The same time grid, one column wide. The most room per event, so the natural target for a “+N more” click.
yearTwelve monthsOne year Twelve mini grids. Events are drawn as coloured dots plus a +N badge, not as pills.
listOne Jalali monthOne month The same range as month view, rendered as a chronological list. Best on narrow screens and for screen readers.

Choosing and switching

const cal = Zarvan.create({ selector: "#calendar", view: "week" });

cal.getView();            // "week"
cal.setView("month");     // switch; emits onViewChange
cal.getViews();           // ["day","week","month","year","list"] — enabled ones, in switcher order

Week and day keep an anchor date of their own, so switching between them does not lose the day you were looking at. Month, year and list share one. gotoDate() moves every view's anchor, which is what makes “jump to this date, then switch view” land where you expect.

Removing a view

A view that is turned off disappears from the switcher and from getViews(), and setView() on it warns with warn.viewDisabled. If the current view is disabled at construction, the calendar falls back — to month when it is available, otherwise to the first enabled view in registry order. 

Zarvan.create({
  selector: "#calendar",
  view: "week",
  features: {
    views: { year: false, list: false },   // a three-view calendar
  },
});

The “+N more” affordance

Month view measures how many events fit in a day cell and collapses the remainder. Clicking the remainder emits onMoreEventsClick and — unless features.moreEventsModal is off — opens a modal listing that day's events. The modal is a real dialog: focus moves into it, Tab cycles inside it, Esc closes it and focus returns to the opener. 

Zarvan.create({
  selector: "#calendar",
  features: { moreEventsModal: false },     // suppress the built-in modal
  handlers: {
    onMoreEventsClick: (p) => {
      // p.date = { gdate, jdate }, p.events = the full list, p.view = "month"
      openMyOwnPanel(p.events);
    },
  },
});

Views

Time-grid layout

Week and day share one engine. What differs between them is the DOM shell; what they have in common is the hour gutter, the now indicator, and the hard part — deciding where two events that collide should go.

Live
Layout
overlapFocus
Five events, four of them colliding. Switch the layout, then hover one of the overlapping pills with overlapFocus on.

Two answers to the same question

overlap — the default

Colliding events cascade with a visible offset, each one slightly narrower and inset from the one behind it. Nothing is ever reduced to a sliver, so a day with eight overlapping events is still readable; the cost is that the later ones are partly covered.

columns

Colliding events are packed side by side, the way Google Calendar does it. Every event is fully visible; the cost is that a busy hour divides into narrow columns. 

Zarvan.create({
  selector: "#calendar",
  view: "week",
  features: { timeGridLayout: "columns" },   // "overlap" (default) | "columns"
});

cal.setOption("features.timeGridLayout", "overlap");   // hot

overlapFocus

With overlap, the pill underneath is partly hidden. overlapFocus is the answer: hovering or focusing one event of a colliding group dims the others and lifts the one you are pointing at. It is on by default and costs nothing when nothing collides.

The animation and dim values are written by the renderer as custom properties, so the effect can be retuned or switched off without a second stylesheet: 

.zc-calendar {
  --zc-ov-duration: .18s;
  --zc-ov-easing: ease;
  --zc-ov-delay: 0s;
  --zc-ov-dim-opacity: .07;   /* how far the others fade */
}

The vertical scale

One token drives the whole grid: --zc-hour-height, 60px by default, meaning one pixel per minute. Everything positioned on the grid — events, the hour lines, the now indicator — is derived from it, so changing it rescales the day rather than breaking it. 

.zc-calendar { --zc-hour-height: 44px; }   /* a denser day */

The all-day row

An event is all-day if allDay is set, if start has no time component, or if it spans more than one day. All-day events are drawn in a row above the time grid rather than inside it, because a bar that runs the full height of the day is not information.

A multi-day event that should sit on the grid — an overnight shift, say — opts back in with forceTimed: true. 

{ title: "اسپرینت", start: "1405-06-03", end: "1405-06-07", allDay: true }
{ title: "شیفت شب", start: "1405-06-03T22:00", end: "1405-06-04T06:00", forceTimed: true }

features.allDayRow: false removes the row; features.allDayBar: false keeps the row but stops drawing the continuous bar across the days an event spans.

The now indicator

A red line at the current time on today's column, updating on a 30-second tick. It is a plugin — now-indicator — not core, and it can be removed entirely by leaving it out of options.plugins. features.autoScrollToNow (off by default) additionally scrolls the grid to it when the view renders. 

Zarvan.create({
  selector: "#calendar",
  view: "day",
  features: { nowLine: true, autoScrollToNow: true },
});

The event object

A plain object with Jalali date strings. No Date instances, no timezone arithmetic, no wrapper class to construct.

Live One of each kind, in week view.
Timed on the grid, all-day and multi-day in the row above it, and one multi-day event forced back onto the grid with forceTimed. 
{
  id: 1,                                 // any comparable value; needed for updateEvent/removeEvent
  title: "جلسه طراحی",
  start: "1405-06-02T09:00",             // "YYYY-M-D" or "YYYY-M-DTHH:MM", padding optional
  end: "1405-06-02T10:30",               // defaults to start
  type: "meeting",                       // drives colour and filtering
  allDay: false,
  forceTimed: false,                     // keep a multi-day event on the time grid
  repeat: { freq, interval, until, count, byWeekday },
}

Dates are Jalali strings

"YYYY-M-D" for an all-day event, "YYYY-M-DTHH:MM" for a timed one. Zero-padding is optional — "1405-6-2" and "1405-06-02" are the same date. 

{ id: 1, title: "استندآپ", start: "1405-06-02T09:00", end: "1405-06-02T09:15" }
{ id: 2, title: "تعطیل",   start: "1405-06-05", allDay: true }
{ id: 3, title: "اسپرینت", start: "1405-06-02", end: "1405-06-05" }        // multi-day ⇒ all-day
Gregorian dates in, Jalali strings out

Gregorian Date objects appear only where you talk to something outside the calendar: in callback payloads, in getVisibleRange(), and in the range handed to a lazy loader. Everything you pass in is a Jalali string. See Jalali dates for converting between the two.

When an event counts as all-day

Three ways, and any one of them is enough:

  1. allDay: true is set explicitly.
  2. start has no time component — "1405-06-05" rather than "1405-06-05T09:00".
  3. It spans more than one day and forceTimed is not set.

Ids

An id can be any comparable value — a number, a string, a UUID. It is what getEventById(), updateEvent() and removeEvent() match on, so an event without one is display-only. Set validation.requireNumericId if your backend guarantees numeric ids and you would rather catch a string early.

Types

type is a free string. It drives the colour of the pill, the entry in the type filter, and the label shown for it. A type with no entry in typeStyles gets a stable auto-colour derived from the name itself, so a new type is never invisible. See Types and colours.

What happens to a bad event

It is reported through onWarn with a stable code and dropped — the calendar does not throw, and it does not render half an event. validation.onInvalid: "keep" keeps it instead and flags it _invalid; validation.autoFix repairs an end that falls strictly before start rather than rejecting it. 

Zarvan.create({
  selector: "#calendar",
  events: [{ id: 1, title: "خراب", start: "not-a-date" }],
  handlers: {
    onWarn: (p) => console.warn(p.code, p.extra),   // "warn.invalidStart", { reason: "bad_date" }
  },
});

Switch on p.code, never on p.message — the message is localised and will change with the locale.

Saturday is zero

byWeekday follows the Jalali week, which starts on Saturday. It is not the JavaScript Date.getDay() numbering, where Sunday is zero. [5, 6] is the Persian weekend — Thursday and Friday.

How expansion works

The stored list keeps one object per recurring event. On every render the calendar expands the rule across the visible range only, so getEvents() returns your original list while the grid shows the occurrences. Each occurrence carries the parent's id and title, so onEventClick hands you an event you can look up. 

cal.getEvents().length;      // 1 — the rule

// What the current view is actually drawing:
const r = cal.getVisibleRange();
// (the same expansion a plugin gets through ctx.expandRecurring)

Editing one occurrence of a series is not something the rule can express — change the rule and add a one-off event, which is what a calendar server does under the covers anyway.

typeStyles

A map from type name to { bg, color }. Both are plain CSS colour values, so rgb(), hsl() and var(--your-token) all work. 

Zarvan.create({
  selector: "#calendar",
  events,
  typeStyles: {

    holiday: { bg: "#dc2626", color: "#fff" },
  },

cal.setTypeStyles({ meeting: { bg: "#e11d48" } });   // replaces the whole map

Types you did not style

A type with no entry is not left grey. The library hashes the type name into a hue and produces hsl(hue, 70%, 45%) with white ink — deterministic, so the same type is the same colour on every page load and in every instance, and a type your backend invents this morning is still legible this afternoon.

Worth knowing

This is why you can ship without typeStyles at all. Add entries only for the types whose colour is part of your product's language; let the rest auto-colour.

How the colours get in

The calendar injects one CSS rule per type, scoped to its instance, setting two custom properties. The stylesheet decides which elements consume them — the pill background, the month dot, the year dot, the list dot — so a new event-coloured element is a CSS change, not a JavaScript one. 

/* what the injector writes, per instance */
[data-zc-id="zc4f2a1b"] .zc-type-meeting {
  --zc-event-bg: #2563eb;
  --zc-event-fg: #fff;
}

features.typeStyleInjection: false stops the injection entirely, which is what you want if you would rather write the type rules in your own stylesheet.

typeLabels

The type is a key, not a caption. typeLabels maps it to what the reader sees, in the type filter dropdown and in the exported spreadsheet. A type with no label shows its raw key. 

Zarvan.create({
  selector: "#calendar",
  typeLabels: { meeting: "جلسه", task: "کار", holiday: "تعطیل" },
});

cal.setOption("typeLabels", { meeting: "پیگیری" });   // hot
Dark mode leaves these alone

typeStyles colours do not follow the colour scheme — a brand colour is not the library's to reinterpret. If one of yours does not survive on a dark ground, set a different map from an onColorSchemeChange listener. See Dark mode.

Events

Clicks and callbacks

Every callback has the same signature: (payload, meta, ctx). Click an event below and watch what actually arrives.

Live
Click a pill, double-click it, right-click it, tab to it, click a day number, open the sidebar, navigate. Every one of those is a callback.

One signature

Every callback receives three arguments, always in the same order and always present. meta is null rather than absent for callbacks that have none, so destructuring is safe. 

Zarvan.create({
  selector: "#calendar",
  handlers: {
    onEventClick: (event, meta, ctx) => {
      event.title;        // the event object
      meta.view;          // "month" | "week" | …
      meta.jdate;         // { jy, jm, jd } — the day it was clicked on
      meta.gdate;         // the same day as a Gregorian Date
      meta.isAllDay;      // whether it was drawn as an all-day event
      meta.element;       // the DOM node it was drawn as
      meta.domEvent;      // the original DOM event
      ctx.instanceId;     // which calendar, when you run more than one
    },
  },
});

Two ways to subscribe

handlers at construction, or .on() at any time. They are the same bus and the same set of names; .on() returns its own unsubscribe function. 

const off = cal.on("onEventClick", (ev) => console.log(ev.title));
off();                                  // unsubscribe

cal.off("onEventClick", myHandler);     // or by reference
cal.emit("myOwnEvent", { … });          // the bus is yours too
A thrown handler cannot break the calendar

Each subscriber is called in isolation. One that throws is reported to the console and the rest still run — a bug in your click handler does not stop the calendar from rendering.

meta.element

The node the event was drawn as. This is the right anchor for a popover, and it is better than the two things you might otherwise reach for: domEvent.currentTarget is the same node but only while the event is being dispatched, and domEvent.target is a child in some views — a list row's title, a month timed row's title span. 

onEventClick: (ev, meta) => {
  const box = meta.element.getBoundingClientRect();
  showPopover(box, ev);
}
Do not hold on to it

Any re-render replaces the node. Do not keep meta.element across navigation, a view change, a filter change or a data change — read it, use it, drop it.

Finding event nodes yourself

Every node that stands for an event carries zc-event-node, whichever view drew it. .zc-event cannot serve that purpose — it carries the pill's colours, and three of the six event nodes never have it (month timed rows, list rows and modal rows). 

document.addEventListener("click", (e) => {
  const node = e.target.closest(".zc-event-node");   // works in every view
  if (node) { /* … */ }
});

zc-event-node is a marker only: no rule in the stylesheet targets it, so it is safe to key your own CSS off it.

Turning interactions off

features.interactions decides which DOM events reach the bus at all. Turning one off means the listener is never attached, not that the callback is filtered afterwards. 

features: {
  interactions: { click: true, dblClick: false, hover: false, contextMenu: false, focus: true },
}

// or the whole bus at once — no callback fires, for anything
features: { events: false }

Watching for changes

Every mutation emits onEventsChange with what kind it was, which event it concerned and the full list afterwards. 

cal.on("onEventsChange", (p) => {
  p.type;      // "add" | "update" | "remove" | "set" | "load"
  p.event;     // the event concerned, or null for "set" and "load"
  p.events;    // the whole list afterwards
});

"load" only appears when events is a function — see Loading on demand.

Mutations and rendering

A mutation schedules a render rather than performing one, so a loop of a hundred addEvent() calls costs one render, not a hundred. Call refresh() if you need the DOM updated before the next line runs. 

incoming.forEach((ev) => cal.addEvent(ev));   // still one render
cal.refresh();                                // …unless you ask for it now

expect(root.querySelectorAll(".zc-event-node")).toHaveLength(incoming.length);

Loading events on demand

An array keeps every event in memory for the life of the page — fine for hundreds, hopeless for years of history. Pass a function instead and the calendar asks for one visible range at a time.

A simulated backend. Page forward and back and watch the log: the second visit to a month does not call the loader again, because that range is cached. Turn the latency up and you will see the hairline progress bar across the top of the grid.

The loader

Zarvan.create({
  selector: "#calendar",
  events: async ({ startG, endG, startJ, endJ, view }) => {
    const res = await fetch(`/api/events?from=${startG.toISOString()}&to=${endG.toISOString()}`);
    return res.json();     // an array of events, or a promise of one
  },
});
FieldTypeWhat it is
startG / endGDateGregorian, inclusive — what a backend speaks.

What it handles for you

When it asks

On the visible range changing: navigation, and switching view. A re-render that leaves the range where it is — filtering, searching, a local edit — does not re-request.

Out-of-order answers

Every request carries a generation, and a result whose generation is no longer current is discarded. Paging forward twice quickly cannot leave the slower request's events on screen — which is the bug this design exists to prevent.

De-duplication and caching

Two asks for one range share a single call. Fetched ranges are remembered in a capped cache (eventCacheLimit, default 12), so paging back and forth does not re-request.

Replace, not merge

What comes back replaces what was loaded. The source is the authority for the range it was asked about; merging would quietly accumulate events from months the reader has long since navigated away from — in memory, in getEvents(), and in the Excel export.

Failures

A rejected load leaves what is on screen alone rather than blanking the calendar, reports through onEventsLoadError and onError, and is not cached — so simply returning to that range tries again. A load still in flight when destroy() runs is ignored rather than resolving into a torn-down calendar.

Local edits against a lazy source

addEvent / updateEvent / removeEvent show immediately and are not overwritten on the visible range. They drop the cache, so navigating away and back reloads from the source. Persist them through your own API; call refetchEvents() when you want the source's version now. 

await api.save(draft);
cal.addEvent(draft);        // optimistic — shows at once
cal.refetchEvents();        // …or take the server's word for it

Showing that it is working

While any load is outstanding the container carries zc-is-loading, which draws a hairline progress bar across the top of the grid — suppressed under prefers-reduced-motion. Style that class for anything heavier. 

cal.isLazy();      // true — events is a function
cal.isLoading();   // true while a fetch is outstanding

cal.on("onEventsLoadStart", () => spinner.show());
cal.on("onEventsLoadEnd",   () => spinner.hide());
cal.on("onEventsLoadError", (p) => toast(p.error.message));
.zc-calendar.zc-is-loading .zc-body { opacity: .6; }

Switching sources

setEvents() takes either kind, so you can move between them at runtime.

cal.setEvents(myLoaderFunction);   // become lazy
cal.setEvents([...]);              // go back to an array; refetchEvents() now returns false

Jumping to a date

gotoDate() takes either a Gregorian Date or a Jalali { jy, jm, jd }. It returns the resulting Date, or null if what you passed was not a date — in which case nothing moves.

It moves every view

Week and day keep their own anchor so that switching between them does not lose your place — but gotoDate() deliberately moves all of them. That is what makes “jump to this date, then switch to week view” land on the week you asked for.

Asking where you are

cal.getDate();           // Date — the active view's anchor
cal.getJDate();          // { jy, jm, jd } — the same, in Jalali
cal.getVisibleRange();   // { startG, endG } — Gregorian Dates, copies, inclusive

getVisibleRange() is the range the current view covers, which is what you would send to a backend. It is also exactly what a lazy loader is asked for, and what the Excel export writes out.

Knowing when it moved

cal.on("onDateChange", (p) => {
  p.from;      // Date — where the anchor was
  p.to;        // Date — where it is now
  p.source;    // "next" | "prev" | "today" | "gotoDate" | "mini" | "api" | "internal"
});

cal.on("onRangeChange", (p) => {
  p.startG; p.endG; p.view;    // fires when the covered range moves — the lazy-load trigger
});

onDateChange fires only when the anchor day actually changes, so a re-render in place does not emit one. onRangeChange is the coarser signal: it fires when the covered range moves, which is also what triggers a fetch from a lazy source.

The filter state

One object, two fields, and it survives navigation and view switches — filtering is a property of the calendar, not of the view you happen to be looking at. 

cal.on("onFiltersChange", (p) => {
  p.type;     // the selected type, or "__all__"
  p.q;        // the search string
  p.source;   // "type" | "search" | "autocomplete" | "clear"
});

What the search matches

Event titles, case-insensitively, with Persian and Arabic character forms normalised so that ي/ی and ك/ک match each other — which they must, or half of what users type finds nothing. Numerals are normalised the same way, so typing Latin digits finds events whose titles use Persian ones.

The suggestion list

Suggestions are drawn from the titles in the currently loaded range, after the type filter but before the search filter — so narrowing by type narrows the suggestions, and typing does not make the list you are choosing from disappear underneath you.

The list never takes focus. The input keeps it and points at the highlighted row with aria-activedescendant, which is what lets ↑ ↓ work while you are still typing. Choosing one emits onAutocompleteSelect with the chosen title, and then onFiltersChange with source: "autocomplete".

  autocomplete: false,   // keep the search box, drop the suggestions
}

The rule

Two rules to remember

All when clauses must match — they are ANDed, not ORed. And later rules override earlier ones, so put the general rule first and the exception after it. when may be omitted entirely and its keys written at the top level.

In CSS

The supported path, and the one you will use most: set the tokens on the container.

.zc-calendar {
  --zc-color-accent: #e11d48;
  --zc-color-surface: #fff;
  --zc-font-family: inherit;
  --zc-month-row-height: 160px;
  --zc-radius-lg: 4px;

Custom properties pierce a shadow boundary, so this keeps working in shadow: true mode — which no other override technique does.

At runtime

cal.setTheme({ "color-accent": "#e11d48" });      // bare names are namespaced
cal.setTheme({ "--zc-color-accent": "#e11d48" }); // …so these two are identical

cal.setTheme({ "color-accent": null });           // null clears the override

setTheme() writes inline custom properties on the container. The instance remembers which ones it wrote, so destroy() removes its own and only its own — tokens the host set on that element before create() ran are left alone.

Fonts

The core stylesheet forces no font. It sets font-family: var(--zc-font-family) and defaults that token to inherit, so the calendar takes your application's typeface by default. Load the optional theme file to use the bundled Vazir face instead, or set the token. 

.zc-calendar { --zc-font-family: "IRANSans", system-ui, sans-serif; }

When tokens are not enough

The stylesheet is deliberately not wrapped in an @layer. Layers were tried and rejected: unlayered host CSS beats layered CSS at any specificity, which is fine for a host that deliberately targets .zc-* classes but also waves through collateral damage — a global reset in your app would win over the library's reset and break the layout.

What ships instead is a specificity contract:

RulesSelector shapeSpecificityBeats

components / views.zc-calendar .zc-x(0,2,0)the reset
state.zc-calendar .zc-x.zc-is-y(0,3,0)the view rules

To restyle beyond tokens, write a selector at (0,2,0) or higher:

.zc-calendar .zc-day-cell { background: #fafafa; }     /* (0,2,0) — beats the view rule */

Dark mode

The same tokens, re-valued under one class. Not a second stylesheet — so a calendar you have already themed goes dark with everything else.

Live

This calendar keeps its own scheme, so you can set it against the page. Choose auto and then change your operating system's appearance — it follows, with no reload. (Every other demo on this site follows the site's theme toggle instead.)

Setting it

Zarvan.create({ selector: "#calendar", colorScheme: "auto" });   // "light" | "dark" | "auto"

cal.setColorScheme("dark");
cal.getColorScheme();          // "dark" — the setting, which may be "auto"
cal.getResolvedColorScheme();  // "dark" — what is on screen, never "auto"

cal.setOption("colorScheme", "light");   // it is a hot option too

The default is "light", so adding the library to an existing page changes nothing about how it looks. Changing the scheme does not re-render — the DOM is the same either way; only which custom properties apply changes.

How "auto" works

"auto" is resolved in JavaScript rather than by a @media (prefers-color-scheme: dark) block. Either would work; this way the dark palette is written once instead of duplicated into a media block that then has to be kept in step with the class it duplicates.

The practical difference is that "auto" keeps following the system rather than being sampled at construction. The matchMedia listener is attached only while "auto" is in force and is registered on the instance store, so destroy() takes it along with everything else. 

cal.on("onColorSchemeChange", (p) => {
  p.scheme;     // "light" | "dark" | "auto" — the setting
  p.resolved;   // "light" | "dark" — what is on screen
  p.source;     // "api" when you changed it, "system" when the OS did

  document.body.classList.toggle("dark", p.resolved === "dark");
});

How it works

A zc-scheme-dark class is stamped on the .zc-calendar element and — separately — on the modal overlay, which is appended to <body> rather than to the calendar and so inherits none of its custom properties. The class carries nothing but re-valued colour tokens at (0,2,0) specificity, which beats the (0,1,0) defaults and loses to your inline setTheme() overrides. 

/* what the class does, in outline */
.zc-calendar.zc-scheme-dark {
  color-scheme: dark;
  --zc-color-accent: #8ab4f8;
  --zc-color-surface: #1b1c1f;
  --zc-color-text: #e3e3e6;
  --zc-color-on-accent: #10223d;   /* ink inverts: dark text on a light accent */
  /* …and the rest of the colour scale */
}

You can set that class yourself if you would rather not go through the API — but then "auto" is yours to track.

Two things that do not follow

Both deliberately:

  • typeStyles colours. They are yours, and a brand colour is not the library's to reinterpret. Types with no entry take the accent, which does follow.
  • Tokens written by setTheme(). Those land as inline custom properties, so they win in both schemes. 
// Give each scheme its own palette
cal.on("onColorSchemeChange", ({ resolved }) => {
  cal.setTypeStyles(resolved === "dark" ? DARK_TYPES : LIGHT_TYPES);
  cal.setTheme(resolved === "dark" ? { "color-accent": "#a5b4fc" } : { "color-accent": "#4f46e5" });
});

The background

In dark mode the calendar paints its own ground, because a dark widget cannot leave its padding to a light host page. That is --zc-color-canvas, and in light mode it is transparent — so a light calendar still shows whatever your page put behind it, exactly as before dark mode existed.

Wording and numerals

Zarvan is a Persian calendar, and that is a decision rather than a default. What a locale does control is wording and numerals — and everything you do not name is inherited.

Three things you cannot change

  • The calendar system is Jalali. There is no Gregorian mode. Gregorian Date objects appear only in callback payloads and getVisibleRange(), where they exist so you can talk to a backend.
  • The layout is right-to-left, always. The stylesheet is written that way throughout; there is no direction option and a locale cannot carry one. The container is stamped dir="rtl".
  • Persian is the only bundled locale. There is no English locale.
Why

Decided once, so none of it is a runtime branch that can be got wrong. A calendar that is sometimes RTL and sometimes not has two layouts to test, two sets of bugs, and a direction token somebody will eventually set incorrectly.

Jalali dates

The date arithmetic ships inside zarvan.js. You get the jalaali global along with Zarvan — one script tag, no second dependency and no load order to get wrong.

Both boxes are wired to the jalaali global that came with the library. Below them, year view — twelve Jalali months, each with its own length.

The format the calendar takes

"YYYY-M-D" for a date, "YYYY-M-DTHH:MM" for a moment. Zero-padding is optional. This is deliberately not ISO 8601: an ISO string means a Gregorian date, and accepting one here would be ambiguous about which calendar the numbers belong to. 

"1405-06-02"         // 2 Shahrivar 1405
"1405-6-2"           // the same date
"1405-06-02T09:00"   // 09:00 on that day

Converting

jalaali.toJalaali(2026, 8, 27);        // { jy: 1405, jm: 6, jd: 5 }
jalaali.toJalaali(new Date());         // a Date works too

jalaali.toGregorian(1405, 6, 5);       // { gy: 2026, gm: 8, gd: 27 }
jalaali.jalaaliToDateObject(1405, 6, 5);   // a real Date

jalaali.isValidJalaaliDate(1405, 12, 30);  // false — 1405 is not a leap year
jalaali.isLeapJalaaliYear(1403);           // true
jalaali.jalaaliMonthLength(1405, 12);      // 29
jalaali.jalaaliWeek(1405, 6, 5);           // { saturday, friday } — the week it falls in

Talking to a backend

Most servers speak Gregorian. The calendar hands you Gregorian Date objects everywhere a backend is the likely next stop — callback payloads, getVisibleRange(), and the range given to a lazy loader — so the conversion usually is not yours to do at all. 

// Loading: the range arrives Gregorian, ready to send
events: async ({ startG, endG }) => {
  const res = await fetch(`/api/events?from=${startG.toISOString()}&to=${endG.toISOString()}`);
  const rows = await res.json();

  // Coming back the other way, convert once, at the boundary
  return rows.map((row) => {
    const d = new Date(row.starts_at);
    const j = jalaali.toJalaali(d);
    const pad = (n) => String(n).padStart(2, "0");
    return {
      id: row.id,
      title: row.title,
      type: row.kind,
      start: `${j.jy}-${pad(j.jm)}-${pad(j.jd)}T${pad(d.getHours())}:${pad(d.getMinutes())}`,
    };
  });
}
Convert at the edge

Do the conversion where data enters and leaves your application, not in the middle of it. One function in, one function out — then everything between them speaks a single calendar and there is no “which kind of date is this?” to get wrong.

The week

The Jalali week runs Saturday to Friday, and Saturday is index 0 everywhere the library counts weekdays — in repeat.byWeekday, in a highlight rule's when.weekday, and in the order of a locale's weekdays array. Thursday and Friday, [5, 6], are the Persian weekend.

Not Date.getDay()

JavaScript numbers Sunday as 0. Converting between the two is (date.getDay() + 1) % 7.

Plugins

The shape

A name, an install function, and an uninstall function returned from it. That returned function is not optional bookkeeping — it is what makes destroy() complete. 

const eventCounter = {
  name: "event-counter",

  install(cal) {
    let badge = null;

    // A hook fires when the calendar builds the thing it names.
    const offSidebar = cal.hooks.on("sidebar", (p) => {
      badge = document.createElement("div");
      p.el.appendChild(badge);
      update();
    });

    const offRender = cal.on("onRenderEnd", update);

    function update() {
      if (!badge) return;
      const range = cal.getVisibleRange();
      const list = cal.applyFilters(cal.expandRecurring(cal.getEvents(), range.startG, range.endG));
      badge.textContent = cal.num(list.length) + " رویداد در این بازه";
    }

    // A plugin may add public methods to the instance.
    cal.api.countVisibleEvents = () => { /* … */ };

    return function uninstall() {
      offSidebar();
      offRender();
      if (badge) badge.remove();
      delete cal.api.countVisibleEvents;
    };
  },
};

The hooks

Four, each firing when the calendar builds the thing it names. This is the extension surface that lets a plugin decorate rendering without knowing how rendering works.

HookPayloadFires for

Two stores, and the difference matters

cal.store lives until destroy(). The store on the timeColumn payload is the render store, released at the top of every render. Anything you set up per column — an interval, a listener — belongs on the render store, or you leak one of them per column per render.

The contract

Rendering

render(ctx) is handed a view context rather than the DOM — everything a renderer needs, passed explicitly instead of reached for through the enclosing scope. Find the body through the instance id the container is stamped with: 

render(ctx) {
  const root = document.querySelector(`[data-zc-id="${ctx.instanceId}"]`);
  const body = root && root.querySelector(".zc-body");
  if (!body) return;
  body.innerHTML = "";

  const events = ctx.eventsFor({ jy, jm, jd });     // already filtered and expanded

  for (const ev of events) {
    const pill = document.createElement("div");
    pill.className = "zc-event";
    pill.textContent = ev.title;

    // The one call that matters: the event bus, keyboard activation,
    // the ARIA role and the zc-event-node marker, all at once.
    ctx.bindEventItem(pill, ev, { jdate, isAllDay: false });

    lane.appendChild(pill);
  }

  // Lets highlight rules and the dayElement hook reach your view too.
  ctx.decorateDay(lane, gdate, jdate, "timeline");

  body.appendChild(wrap);
}

Adding a view used to mean finding all nine. There are now zero such comparisons in the codebase, which is the reason your view can join without touching any of it.

Shadow DOM

The calendar defends itself with a scoped reset and a specificity contract. For hosts that fight dirty, shadow: true closes the last gap.

Live · shadow: true
…the rest of this page will suffer; the calendar will not.
The hostile stylesheet sets border, text-transform and letter-spacing on every div, span and button with !important. Nothing crosses the shadow boundary. Press the button again to remove it.

Turning it on

Zarvan.create({
  selector: "#calendar",
  shadow: true,
  styles: zarvanCssText,     // see below
});

Why `styles` exists

A <link> in the light DOM does not cross a shadow boundary, so the calendar has to put the stylesheet inside the shadow tree. It tries to read it from document.styleSheets on its own, which works when the sheet is same-origin — as it is on this page. A stylesheet served from a cross-origin CDN cannot be read that way, and that is what options.styles is for. 

// a string of CSS
const css = await fetch("/vendor/zarvan/zarvan.css").then((r) => r.text());
Zarvan.create({ selector: "#calendar", shadow: true, styles: css });

// a constructed stylesheet, or an array of either
const sheet = new CSSStyleSheet();
sheet.replaceSync(css);
Zarvan.create({ selector: "#calendar", shadow: true, styles: [sheet, myOverrides] });

If shadow mode finds no stylesheet to adopt, it warns clearly rather than rendering an unstyled calendar in silence. If the browser has no Shadow DOM at all, it warns and renders in the light DOM instead.

Three elements, not one

In shadow mode the calendar renders into a div inside a shadow root rather than into the host itself, so the host keeps whatever layout role your page gave it. 

cal.getContainer();    // the element you passed to create()
cal.getRoot();         // the .zc-calendar element inside the shadow root
cal.getShadowRoot();   // the shadow root, or null in the light DOM

Outside shadow mode, getContainer() and getRoot() are the same element. A shadow root cannot be detached once attached, so destroy() removes the rendering div instead.

What changes in shadow mode

  • Design tokens still work. Custom properties inherit through a shadow boundary, so .zc-calendar { --zc-color-accent: … } on the host still themes the calendar. This is the only override technique that survives, which is the argument for theming through tokens in the first place.
  • Plain CSS overrides do not. A host rule targeting .zc-day-cell never reaches inside. Pass your overrides through options.styles instead.
  • The modal moves. It is appended to the shadow root rather than to <body>, because a node in the light DOM would not be reached by the adopted stylesheet.
  • document.activeElement reports the host. Anything of yours that cares where focus actually is must ask getShadowRoot().activeElement.
You probably do not need it

The scoped reset handles ordinary hostility — a global * { box-sizing }, an aggressive button rule, a CSS framework's base layer. The repository's test/host-hostile.html asserts that every structural property is byte-identical with a deliberately hostile stylesheet toggled on and off. Reach for shadow mode when you are embedding into a page you do not control at all.

Roving tab stops

The day grids use the roving-tabindex pattern: the grid is one tab stop and the arrow keys move within it. A year view is therefore 12 tab stops rather than 372 — the difference between a calendar a keyboard user can pass through and one they must escape.

The collapsed sidebar

width: 0 plus overflow: hidden hides the sidebar to the eye only. Its search box, dropdown, mini calendar and export button would stay focusable and stay in the accessibility tree, so tabbing through a collapsed calendar walked into a panel nobody could see.

It is marked inert while collapsed, with aria-hidden alongside it as the fallback for browsers without inert — which hides it from assistive technology but not from Tab, hence both. Focus is moved out before the panel is inerted, because inerting an ancestor of the focused element drops focus to <body> in some engines and loses the reader's place in the page entirely.

The focus ring

The reset clears outline so the host's focus styling cannot leak in, and --zc-focus-ring is what replaces it.
